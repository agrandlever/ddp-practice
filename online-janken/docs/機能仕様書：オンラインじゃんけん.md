# 機能仕様書：オンラインじゃんけん

## 1. 前提

- 同時に対戦へ参加できるユーザーは2人までとする。
- 3人目のユーザーがアクセスした場合は、対戦には参加させず、参加上限エラーを表示する。
- 対戦部屋の作成、招待URL、ユーザー登録などによる対戦相手の識別機能は設けない。
- 同一ユーザーがページを再読み込みまたは再アクセスしても、新しい参加ユーザーとして数えない。
- 2人のユーザーがサイトへ参加した時点で、自動的に対戦を開始する。

---

## 2. 要件とユースケースの対応

| 要件ID | 機能名 | ユースケースID | ユースケース名 |
|---|---|---|---|
| `FR-001` | 対戦開始 | `UC-001` | 対戦を開始する |
| `FR-002` | 手の選択 | `UC-002` | じゃんけんの手を選択する |
| `FR-003` | 勝敗判定・表示 | `UC-003` | 対戦結果を確認する |

# 3. ユースケース

## UC-001｜対戦を開始する

### アクター

一般ユーザー

### 事前条件

- ユーザーがオンラインじゃんけんサイトへアクセスできる。

### 事後条件

- 2人のユーザーが対戦に参加している。
- 2人とも`SCR-002｜手の選択画面`が表示され、じゃんけんの手を選択できる。

### 正常系フロー

1. 1人目のユーザーが`SCR-001｜初期・待機画面`へアクセスする。
2. システムは、アクセスしている参加ユーザーが1人であることを確認する。
3. システムは`MSG-001「対戦相手を待っています」`を表示する。
4. 2人目のユーザーが`SCR-001｜初期・待機画面`へアクセスする。
5. システムは2人のユーザーが揃ったことを確認する。
6. システムは自動的に対戦を開始する。
7. システムは2人とも`SCR-002｜手の選択画面`へ遷移させる。

### 代替フロー

#### 1a｜同一ユーザーの再読み込み・再アクセス

1. すでに参加中のユーザーが`SCR-001｜初期・待機画面`を再読み込みまたは再アクセスする。
2. システムは同一ユーザーとして扱う。
3. システムは新しい参加ユーザーとして人数を増やさない。
4. 現在の対戦状態に応じた画面を表示する。

#### 4a｜3人目のユーザーがアクセス

1. すでに2人のユーザーが対戦へ参加している状態で、3人目のユーザーがアクセスする。
2. システムは3人目のユーザーを対戦へ参加させない。
3. システムは`SCR-004｜参加上限エラー画面`を表示する。
4. システムは`MSG-009「現在対戦中のため参加できません。」`を表示する。

### 例外フロー

#### E1｜待機中の通信切断

1. 1人目のユーザーが対戦相手を待っている間に、10秒以上そのユーザーとの通信が確認できない。
2. システムはそのユーザーの待機状態を終了する。
3. システムはそのユーザーが使用していた参加枠を解放する。
4. システムは新しいユーザーを1人目の参加者として受け入れられる状態にする。

## UC-002｜じゃんけんの手を選択する

### アクター

一般ユーザー

### 事前条件

- 2人のユーザーが揃っている。
- 対戦が開始されている。
- `SCR-002｜手の選択画面`が表示されている。

### 事後条件

- ユーザーが選択した手が確定している。
- 双方の手が確定した場合は`UC-003｜対戦結果を確認する`へ進む。

### 正常系フロー

1. システムはグー・チョキ・パーの選択肢を表示する。
2. ユーザーはグー・チョキ・パーのいずれか1つを選択する。
3. システムは選択された値を確認する。
4. システムはユーザーが選択した手を確定する。
5. 一度確定した手は、その対戦中は変更できない。
6. システムはユーザー自身が選択した手を表示する。
7. 相手がまだ手を選択していない場合、`MSG-002「対戦相手の選択を待っています」`を表示する。
8. 双方が手を選択するまで、相手が選択した手は表示しない。
9. 双方の手が確定したら`UC-003｜対戦結果を確認する`へ進む。

### 代替フロー

#### 3a｜不正な選択値

1. グー・チョキ・パー以外の値、未入力、または空の値が送信される。
2. システムはその値を受け付けず、手を確定しない。
3. `SCR-002｜手の選択画面`を再表示する。
4. `MSG-008「グー・チョキ・パーのいずれかを選択してください。」`を表示する。
5. 正常系フローの手順2へ戻る。

#### 4a｜確定済みの手を再度送信

1. すでに手を確定したユーザーが、別の手を再度送信する。
2. システムは新しく送信された手を無視する。
3. システムは最初に確定した手を維持する。
4. 相手が未選択の場合は、手の選択画面で相手の選択を待つ。
5. 相手も選択済みの場合は、対戦結果の確認へ進む。

### 例外フロー

#### E1｜対戦相手の通信切断

1. ユーザーが対戦中に、対戦相手との通信を10秒以上確認できない。
2. システムは対戦相手が切断されたと判定する。
3. システムは`MSG-004「対戦相手との通信が切断されました」`を表示する。
4. システムは現在の対戦を終了する。
5. システムは切断したユーザーの参加枠を解放する。
6. システムは残ったユーザーを`SCR-001｜初期・待機画面`へ戻す。
7. システムは新しいユーザーを対戦相手として受け入れられる状態にする。

## UC-003｜対戦結果を確認する

### アクター

一般ユーザー

### 事前条件

- 2人のユーザーが対戦中である。
- 双方のじゃんけんの手が確定している。

### 事後条件

- 対戦結果が表示されている。
- ユーザーは任意のタイミングで初期画面へ戻ることができる。
- 2人とも初期画面へ戻った場合、新しい対戦を開始できる。

### 正常系フロー

1. 2人目のユーザーが手を選択し、双方の手が確定する。
2. システムは双方の手を比較する。
3. システムは通常のじゃんけんルールに従って勝敗を判定する。
4. システムは2人とも自動的に`SCR-003｜結果画面`へ遷移させる。
5. システムは各ユーザーについて、次を表示する。
   - 自分が選択した手
   - 対戦相手が選択した手
   - 勝ち・負け・あいこの結果
6. 勝ったユーザーには`MSG-005「あなたの勝ちです」`を表示する。
7. 負けたユーザーには`MSG-006「あなたの負けです」`を表示する。
8. あいこの場合は双方に`MSG-007「あいこです」`を表示する。
9. システムは「初期画面に戻る」ボタンを表示する。
10. ユーザーがボタンを押すまでは結果画面に留まる。
11. ユーザーが「初期画面に戻る」ボタンを押す。
12. システムはそのユーザーを結果確認済みとして扱う。
13. システムはそのユーザーを`SCR-001｜初期・待機画面`へ戻す。
14. もう一方のユーザーがまだ結果確認済みでない場合、`MSG-001「対戦相手を待っています」`を表示し、`GET /api/status`では`WAITING`を返す。先に戻ったユーザーも現在の2人の参加者の1人として参加枠を保持し、この待機状態には10秒の参加枠解放を適用しない。3人目は引き続き参加できない。
15. 2人とも結果確認済みになった時点で、システムは同じ2人で新しい対戦を自動的に開始する。開始時に両者の手・勝敗・結果確認済み状態を次対戦用に初期化し、開始後は通常の対戦中の通信切断ルールを適用する。
16. システムは2人とも`SCR-002｜手の選択画面`へ遷移させる。

### 例外フロー

#### E1｜結果表示前の通信エラー

1. 双方の手が確定した後、結果を表示するまでの間に通信エラーが発生する。
2. システムは現在の画面に`MSG-003「通信エラーが発生しました。ページを再読み込みしてください。」`を表示する。
3. システムはその対戦を終了する。

## 7.1 MSG-003の内部エラー時の使用

画面系エンドポイントで予期しない内部エラー（`INTERNAL_ERROR`）が発生した場合は、API設計書6.3節に従い、HTTP `500 Internal Server Error`で、エラーが発生したリクエストに対応する現在の画面を表示し、MSG-003を表示する。

| エラーが発生したリクエスト | 表示する画面 | テンプレート |
|---|---|---|
| `GET /` | `SCR-001` 初期・待機画面 | `index` |
| `GET /play` | `SCR-002` 手の選択画面 | `play` |
| `POST /play` | `SCR-002` 手の選択画面 | `play` |
| `GET /result` | `SCR-003` 結果画面 | `result` |
| `POST /result/return` | `SCR-003` 結果画面 | `result` |

新しい共通エラー画面やHTTPエンドポイントは追加せず、内部エラー時のリダイレクトは行わない。`POST /result/return`で内部エラーが発生した場合も`SCR-003`を表示する。

`GET /api/status`で予期しない内部エラーが発生した場合は、既存仕様どおりHTTP `500 Internal Server Error`で、`errorCode`が`INTERNAL_ERROR`、`message`がMSG-003と同じ文言のJSONを返す（API設計書6.3節参照）。

UC-003 E1「結果表示前の通信エラー」の既存フロー（現在の画面へのMSG-003表示と対戦終了）は維持する。本節では、それ以外の内部エラーについて新たな状態変更ルールを定義しない。

# 9. 要件との対応確認

## FR-001｜対戦開始

- `UC-001`で具体化する。
- 1人目は待機状態となる。
- 2人目がアクセスすると自動的に対戦を開始する。
- 2人とも手の選択画面へ遷移する。
- 同一ユーザーの再読み込みでは参加人数を増やさない。
- 同時に参加できるユーザーは2人までとする。
- 3人目がアクセスした場合は対戦へ参加させず、参加上限エラーを表示する。
- 通常の待機状態でユーザーとの通信を10秒以上確認できない場合は、そのユーザーの参加枠を解放する。結果確認後に相手が戻るのを待っている`WAITING`状態は対象外とする。

## FR-002｜手の選択

- `UC-002`で具体化する。
- グー・チョキ・パーから1つ選択する。
- 選択時点で手を確定し、変更できない。
- 再度別の手が送信されても、最初に確定した手を維持する。
- 相手が未選択の場合は待機メッセージを表示する。
- 双方が確定するまで相手の手を表示しない。
- 対戦中に相手との通信を10秒以上確認できない場合は切断と判定し、対戦を終了する。
- 切断後は残ったユーザーを初期・待機状態へ戻す。

## FR-003｜勝敗判定・表示

- `UC-003`で具体化する。
- 双方の手が確定すると勝敗を自動判定する。
- 双方の手と勝ち・負け・あいこを結果画面へ表示する。
- 結果画面から初期画面へ戻ることができる。
- 先に初期画面へ戻ったユーザーは結果確認済みとし、もう一方が戻るまで待機する。`GET /api/status`では`WAITING`を返す。
- この待機中も現在の参加者として参加枠を保持し、10秒の参加枠解放は適用しない。3人目は引き続き参加できない。
- 2人とも結果確認済みになった時点で、同じ2人で新しい対戦を自動開始する。
- 新しい対戦開始時に両者の手・勝敗・結果確認済み状態を次対戦用に初期化し、開始後は通常の対戦中の通信切断ルールを適用する。
- 結果画面表示中は、対戦相手の通信切断を監視しない。

# 10. 既知の制約

## 10.1 結果画面表示中の切断

結果画面では対戦相手の通信切断を監視しない。

そのため、一方のユーザーが結果画面を表示したままブラウザーを閉じ、もう一方のユーザーだけが初期画面へ戻った場合、初期画面へ戻ったユーザーが相手を待ち続ける状態が残る可能性がある。

この動作は、今回の仕様では既知の制約として扱う。

結果確認後に相手が戻るのを待っている`WAITING`状態は、10秒の参加枠解放の対象外である。この間は現在の2人の参加枠を保持するため、3人目は引き続き参加できない。
