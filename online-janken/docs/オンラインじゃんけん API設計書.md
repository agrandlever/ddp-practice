# API設計書：オンラインじゃんけん

## 1. 基本情報

### 1.1 ベースURL

未定。

アプリケーションルートを基準とし、各エンドポイントは`/`から始まる相対パスで定義する。

### 1.2 認証方式

認証なし。

ユーザーID、パスワード、ログイン機能は使用しない。

ただし、1人目と2人目を区別するため、HTTPセッションを使用する。

### 1.3 レスポンス形式

基本レスポンスはHTML（Thymeleaf）とする。

状態確認用エンドポイント`GET /api/status`のみJSONを返す。

| 用途 | レスポンス形式 |
|---|---|
| 画面表示 | HTML（Thymeleaf） |
| 状態確認 | JSON |

### 1.4 ユーザー識別

HTTPセッションを使用する。

用途：

- 1人目と2人目を区別する
- 自分の確定した手を特定する
- 結果画面で自分と相手を区別する
- 各ユーザーが結果画面から初期画面へ戻ったかを管理する

同じHTTPセッションから再アクセス・再読み込みされた場合は、同一ユーザーとして扱い、参加人数を増やさない。

# 2. エンドポイント一覧

| HTTPメソッド | パス | 概要 | Controllerメソッド |
|---|---|---|---|
| `GET` | `/` | 初期・待機画面を表示する | `showHome()` |
| `GET` | `/play` | 手の選択画面を表示する | `showPlay()` |
| `POST` | `/play` | 選択した手を確定する | `submitHand()` |
| `GET` | `/result` | 対戦結果画面を表示する | `showResult()` |
| `POST` | `/result/return` | 結果確認を終了し初期画面へ戻る | `returnToHome()` |
| `GET` | `/api/status` | 現在の対戦状態をJSONで取得する | `getStatus()` |

# 3. エンドポイント詳細

## 3.1 `GET /`

### 概要

初期・待機画面を表示する。

初回アクセス時はHTTPセッションを参加ユーザーとして登録する。

同一セッションから再アクセスされた場合は、新しい参加ユーザーとして登録しない。

### リクエスト

リクエストパラメータなし。

### 正常時

#### 新規参加者が1人目の場合

HTTPステータス：

`200 OK`

テンプレート：

`index`

Model属性：

| 項目 | 型 | 内容 |
|---|---|---|
| `waiting` | `boolean` | 対戦相手を待っている状態か |

`waiting = true`の場合、Thymeleaf側で次を表示する。

`MSG-001「対戦相手を待っています」`

#### 2人揃った場合

新しい対戦を開始する。

HTTPステータス：

`302 Redirect`

遷移先：

`/play`

#### 対戦中の参加済みユーザーがアクセスした場合

自分の手が未選択の場合：

`/play`へリダイレクトする。

自分の手が選択済みで相手待ちの場合：

`/play`へリダイレクトする。

対戦結果が表示可能で、現在のユーザーがまだ結果確認済みでない場合：

`/result`へリダイレクトする。

#### 結果確認済みのユーザーの場合

相手がまだ結果画面にいる場合：

- `200 OK`
- `index`を表示する
- `MSG-001「対戦相手を待っています」`を表示する
- `GET /api/status`では`WAITING`を返す
- 現在の2人の参加者の1人として参加枠を保持し、解放しない
- この待機状態には10秒の参加枠解放を適用せず、3人目は引き続き参加できない

2人とも結果確認済みの場合：

- 同じ2人で新しい対戦を自動的に開始する
- 開始時に両者の手・勝敗・結果確認済み状態を次対戦用に初期化する
- 開始後は通常の対戦中の通信切断ルールを適用する
- `302 Redirect`
- `/play`へリダイレクトする

### 3人目がアクセスした場合

すでに2人が参加中の場合、3人目は対戦へ参加させない。

HTTPステータス：

`409 Conflict`

レスポンス形式：

HTML（Thymeleaf）

テンプレート：

`error/match-full`

エラーコード：

`MATCH_FULL`

表示メッセージ：

`現在対戦中のため参加できません。`

## 3.2 `GET /play`

### 概要

じゃんけんの手の選択画面を表示する。

### リクエスト

リクエストパラメータなし。

### Model属性

| 項目 | 型 | 内容 |
|---|---|---|
| `myHand` | `String` | 自分の確定済みの手 |
| `waitingForOpponent` | `boolean` | 自分の手が確定し、相手の選択を待っているか |

`myHand`の値：

- `rock`
- `scissors`
- `paper`
- 未選択の場合は`null`

### 正常時

#### 自分の手が未選択

HTTPステータス：

`200 OK`

テンプレート：

`play`

表示内容：

- グー
- チョキ
- パー

の選択肢を表示する。

#### 自分の手が選択済みで相手が未選択

HTTPステータス：

`200 OK`

テンプレート：

`play`

表示内容：

- 自分の確定済みの手
- `MSG-002「対戦相手の選択を待っています」`

相手の手は表示しない。

#### 双方の手が確定済み

HTTPステータス：

`302 Redirect`

遷移先：

`/result`

### 対戦開始前の直接アクセス

HTTPステータス：

`302 Redirect`

遷移先：

`/`

## 3.3 `POST /play`

### 概要

ユーザーが選択したじゃんけんの手を送信し、確定する。

### Content-Type

`application/x-www-form-urlencoded`

### リクエストパラメータ

| 項目 | 型 | 必須 | 許可値 |
|---|---|---|---|
| `hand` | `String` | 必須 | `rock` / `scissors` / `paper` |

送信例：

```text
hand=rock
```

画面上では「グー・チョキ・パー」と表示し、送信値には英語の内部値を使用する。

### 正常時

#### 相手が未選択

HTTPステータス：

`200 OK`

`/play`を再表示する。

表示内容：

- 自分の確定した手
- `MSG-002「対戦相手の選択を待っています」`

#### 双方が選択済み

HTTPステータス：

`302 Redirect`

遷移先：

`/result`

### バリデーションエラー

次の場合を不正な入力とする。

- `hand`が未送信
- `hand`が空文字
- `rock`、`scissors`、`paper`以外

HTTPステータス：

`400 Bad Request`

エラーコード：

`VALIDATION_ERROR`

動作：

- 手を確定しない
- `/play`を再表示する
- `MSG-008「グー・チョキ・パーのいずれかを選択してください。」`を表示する

### 対戦開始前に送信された場合

- `hand`を受け付けない
- 手を確定しない

HTTPステータス：

`302 Redirect`

遷移先：

`/`

### 手がすでに確定している場合

新しく送信された`hand`は無視する。

既存の確定済みの手は変更しない。

相手が未選択の場合：

`/play`へリダイレクトする。

相手も選択済みの場合：

`/result`へリダイレクトする。

---

## 3.4 `GET /result`

### 概要

対戦結果を表示する。

### リクエスト

リクエストパラメータなし。

### 正常時

HTTPステータス：

`200 OK`

テンプレート：

`result`

### Model属性

| 項目 | 型 | 内容 | 値 |
|---|---|---|---|
| `myHand` | `String` | 自分の手 | `rock` / `scissors` / `paper` |
| `opponentHand` | `String` | 相手の手 | `rock` / `scissors` / `paper` |
| `result` | `String` | 対戦結果 | `win` / `lose` / `draw` |

### 結果メッセージ

Thymeleaf側で`result`を判定して表示する。

| `result` | メッセージ |
|---|---|
| `win` | `MSG-005「あなたの勝ちです」` |
| `lose` | `MSG-006「あなたの負けです」` |
| `draw` | `MSG-007「あいこです」` |

### 対戦結果が存在しない場合

エラーコードは付与しない。

HTTPステータス：

`302 Redirect`

遷移先：

`/`

### 結果画面表示中の通信監視

`/result`では状態確認のポーリングを行わない。

- 相手の通信状態を監視しない
- ユーザーが「初期画面に戻る」を押すまで結果画面に留まる
- 結果画面表示中に相手が切断しても即時検知しない

---

## 3.5 `POST /result/return`

### 概要

結果画面の「初期画面に戻る」操作を処理する。

現在のユーザーを結果確認済みとして扱い、初期・待機状態へ戻す。

### Content-Type

`application/x-www-form-urlencoded`

### リクエストパラメータ

なし。

### 正常時

現在のHTTPセッションを「結果確認済み」として記録する。

HTTPステータス：

`302 Redirect`

遷移先：

`/`

その後：

#### 相手がまだ戻っていない場合

本人を結果確認済みとして初期・待機画面を表示し、相手を待つ。

- `GET /api/status`では`WAITING`を返す。
- 本人は引き続き現在の2人の参加者の1人として扱い、参加枠は解放しない。
- この待機状態は10秒の参加枠解放の対象外とする。
- 3人目は引き続き参加できない。

#### 2人とも戻った場合

2人とも結果確認済みになった時点で、同じ2人で新しい対戦を自動的に開始する。

開始時に両者の手・勝敗・結果確認済み状態を次対戦用に初期化する。`POST /result/return`の応答は前述のとおり`/`への`302 Redirect`とし、その後`/play`へ遷移する。

新しい対戦開始後は、通常の対戦中の通信切断ルールを適用する。

### 対戦結果が存在しない場合

- 状態を変更しない

HTTPステータス：

`302 Redirect`

遷移先：

`/`

---

## 3.6 `GET /api/status`

### 概要

現在のユーザーから見た対戦状態をJSONで返す。

JavaScriptによる状態確認に使用する。

### リクエストパラメータ

なし。

### 正常時HTTPステータス

`200 OK`

### Content-Type

`application/json`

### レスポンス形式

```json
{
  "status": "WAITING"
}
```

### status一覧

| status | 意味 |
|---|---|
| `WAITING` | 対戦相手を待っている。本人が結果確認済みで、相手がまだ結果確認済みでない場合も含む |
| `PLAYING` | 対戦中で、自分の手を選択できる |
| `WAITING_FOR_OPPONENT` | 自分の手は確定済みで、相手の選択待ち |
| `RESULT_READY` | 双方の手が確定し、結果を表示できる |
| `OPPONENT_DISCONNECTED` | 対戦相手の切断を検知した |

### 対戦に参加していないセッション

HTTPステータス：

`200 OK`

レスポンス：

```json
{
  "status": "WAITING"
}
```

### 本人が結果確認済みで、相手がまだ結果確認済みでない場合

HTTPステータス：

`200 OK`

レスポンス：

```json
{
  "status": "WAITING"
}
```

対戦結果が存在していても、この場合は`RESULT_READY`ではなく`WAITING`を返す。

本人の参加枠は保持し、この待機状態には10秒の参加枠解放を適用しない。3人目は引き続き参加できない。

### 対戦結果が存在し、本人がまだ結果確認済みでない場合

HTTPステータス：

`200 OK`

レスポンス：

```json
{
  "status": "RESULT_READY"
}
```

### 相手の切断を検知した場合

HTTPステータス：

`200 OK`

1回目：

```json
{
  "status": "OPPONENT_DISCONNECTED"
}
```

JavaScriptは`OPPONENT_DISCONNECTED`を受信して対戦相手の切断を検知し、初期・待機画面`/`（`SCR-001`）へ遷移する。

遷移先の`SCR-001`で、`MSG-004「対戦相手との通信が切断されました」`を一度だけ表示する。あわせて、通常の待機メッセージ`MSG-001「対戦相手を待っています」`を表示する。

ページを再読み込みした場合は、切断メッセージを再表示しない。

サーバー側では、5.3節に従って現在の対戦を終了し、切断したユーザーの参加枠を解放する。残ったユーザーは初期・待機状態となり、新しいユーザーを受け入れ可能とする。

`GET /api/status`の`OPPONENT_DISCONNECTED`自体も1回だけ返し、その後は、

```json
{
  "status": "WAITING"
}
```

を返す。

# 4. ポーリング仕様

## 4.1 ポーリング方式

JavaScriptから`GET /api/status`を定期的に呼び出す。

ポーリング間隔：

**2秒**

## 4.2 ポーリング対象

### `/`

2秒ごとに状態を確認する。

用途：

- 2人揃ったか確認する
- 待機ユーザーの生存確認を行う

`PLAYING`になった場合、JavaScriptで`/play`へ遷移する。

### `/play`

2秒ごとに状態を確認する。

用途：

- 相手の手が確定したか確認する
- 相手との通信切断を確認する

`RESULT_READY`になった場合、JavaScriptで`/result`へ遷移する。

### `/result`

ポーリングしない。

# 5. 通信切断・参加枠管理

## 5.1 最終アクセス時刻

`GET /api/status`を受信するたびに、対象ユーザーの最終状態確認時刻を記録する。

## 5.2 対戦中の切断判定

相手ユーザーの最終状態確認から**10秒以上**経過した場合、

`OPPONENT_DISCONNECTED`

と判定する。

## 5.3 切断検知後

- 現在の対戦を終了する
- 切断したユーザーの参加枠を解放する
- サーバー側で残ったユーザーを初期・待機状態へ戻す
- 新しいユーザーを受け入れ可能にする
- `GET /api/status`で`OPPONENT_DISCONNECTED`を1回だけ返し、その後は`WAITING`を返す
- JavaScriptは`OPPONENT_DISCONNECTED`を受信すると、初期・待機画面`/`（`SCR-001`）へ遷移する
- `SCR-001`で`MSG-004「対戦相手との通信が切断されました」`を一度だけ表示し、あわせて`MSG-001「対戦相手を待っています」`を表示する
- ページを再読み込みした場合は、切断メッセージを再表示しない

## 5.4 待機中のユーザー

`WAITING`状態でも、`GET /api/status`を受信するたびに最終状態確認時刻を記録する。

通常の`WAITING`状態では、最後の`GET /api/status`から10秒以上経過した場合：

- 待機状態を解除する
- 参加枠を解放する

ただし、本人が結果確認済みで、相手がまだ結果確認済みでないために待っている`WAITING`状態は、この10秒の参加枠解放の対象外とする。

この場合は現在の2人の参加枠を保持し、3人目は引き続き参加できない。2人とも結果確認済みになった時点で同じ2人による新しい対戦を開始し、開始後は通常の対戦中の通信切断ルールを適用する。

## 5.5 結果画面

`/result`ではポーリングしないため、結果画面を表示したままブラウザーを閉じた場合は即時に切断を検知しない。

# 6. エラーコード定義

| HTTPステータス | エラーコード | 内容 |
|---|---|---|
| `400 Bad Request` | `VALIDATION_ERROR` | `hand`の入力値が不正 |
| `409 Conflict` | `MATCH_FULL` | すでに2人が参加中 |
| `500 Internal Server Error` | `INTERNAL_ERROR` | サーバー内部で予期しないエラーが発生 |

## 6.1 VALIDATION_ERROR

対象：

`POST /play`

表示メッセージ：

`MSG-008「グー・チョキ・パーのいずれかを選択してください。」`

## 6.2 MATCH_FULL

対象：

`GET /`

表示メッセージ：

`現在対戦中のため参加できません。`

## 6.3 INTERNAL_ERROR

対象：

すべてのエンドポイント。

### 画面系エンドポイント

予期しない内部エラーが発生した場合は、HTTPステータスを`500 Internal Server Error`とし、エラーが発生したリクエストに対応する現在の画面をHTML（Thymeleaf）で表示する。

| リクエスト | HTTPステータス | 表示する画面 | テンプレート |
|---|---|---|---|
| `GET /` | `500 Internal Server Error` | `SCR-001` 初期・待機画面 | `index` |
| `GET /play` | `500 Internal Server Error` | `SCR-002` 手の選択画面 | `play` |
| `POST /play` | `500 Internal Server Error` | `SCR-002` 手の選択画面 | `play` |
| `GET /result` | `500 Internal Server Error` | `SCR-003` 結果画面 | `result` |
| `POST /result/return` | `500 Internal Server Error` | `SCR-003` 結果画面 | `result` |

表示する画面には、

`MSG-003「通信エラーが発生しました。ページを再読み込みしてください。」`

を表示する。

新しい共通エラー画面やHTTPエンドポイントは追加しない。`INTERNAL_ERROR`発生時はリダイレクトしない。`POST /result/return`で発生した場合も、`/`へ遷移せず`result`を表示する。

本節は内部エラー時の応答・表示を定義するものであり、新たな状態変更ルールは定義しない。機能仕様書のUC-003 E1「結果表示前の通信エラー」にある対戦終了仕様は維持する。

### 状態確認API

`GET /api/status`で予期しない内部エラーが発生した場合は、既存仕様どおりHTTPステータスを`500 Internal Server Error`、Content-Typeを`application/json`とし、次のJSONを返す。

```json
{
  "errorCode": "INTERNAL_ERROR",
  "message": "通信エラーが発生しました。ページを再読み込みしてください。"
}
```

# 10. 主なバリデーション・ビジネスルール

- じゃんけんの手は`rock`、`scissors`、`paper`のみ受け付ける
- `hand`は必須
- 一度確定した手は変更できない
- 双方の手が確定するまで相手の手を表示しない
- 対戦開始前に`/play`へアクセスした場合は`/`へ戻す
- 対戦結果が存在しない状態で`/result`へアクセスした場合は`/`へ戻す
- 結果画面はユーザーが自分で戻るまで表示する
- 一方だけ結果確認済みの場合は参加枠を保持したまま待機し、`GET /api/status`では`WAITING`を返す。この待機は10秒の参加枠解放の対象外とし、3人目は引き続き参加できない
- 2人とも結果確認を終了したら、同じ2人で新しい対戦を自動的に開始する
- 新しい対戦開始時に両者の手・勝敗・結果確認済み状態を次対戦用に初期化し、開始後は通常の対戦中の通信切断ルールを適用する
- 同一HTTPセッションを複数ユーザーとして登録しない

---

# 11. 既知の制約

## 11.1 利用人数

同時に対戦へ参加できるユーザーは2人までとする。

3人目は`409 Conflict / MATCH_FULL`とする。

## 11.2 結果画面表示中の切断

`/result`ではポーリングを行わない。

そのため、ユーザーが結果画面を表示したままブラウザーを閉じた場合、その切断を即時には検知できない。

一方のユーザーがすでに初期画面へ戻っている場合、相手が結果画面から戻らずブラウザーを閉じると、そのユーザーを待ち続ける状態が残る可能性がある。

これは今回の設計上の既知の制約として扱う。

結果確認後に相手が戻るのを待っている`WAITING`状態は、10秒の参加枠解放の対象外である。この間は現在の2人の参加枠を保持するため、3人目は引き続き参加できない。
