## 1. 目的と前提

DB（データベース）に保存するタスクの構造と、登録・更新・削除時の扱いを定義する。対象は `todos` テーブルの6カラム（保存項目）のみとし、今回指定された定義を採用する。

| 参照資料 | 本書に反映する内容 |
| --- | --- |
| [要件定義書1.1](requirements-todo.md) | 6機能、入力上限、同名タスクの許可、一覧順、H2インメモリ方式 |
| [機能仕様書1.2](functional-spec-todo.md) | 基本情報、編集範囲、完了切替、説明なしの扱い |
| [API設計書1.0](api-todo.md) | 各操作の対象ID、登録・編集の入力項目、操作ごとの変更範囲 |

Java 21、Spring Boot 3.4系、Spring Data JPA（Javaのオブジェクトを通じてDBを読み書きする仕組み）を前提とする。ユーザー、カテゴリ、タグなどのテーブルや追加カラムは設けない。作成日時・更新日時は今回指定された内部管理項目であり、フォームの入力項目や新たな画面表示項目にはしない。

### 1.1 既存資料との差分

要件定義書3.1・6.1、機能仕様書BR-010・9章には「再起動後はタスク0件」とある。本書では今回の初期データ指定を優先し、**起動時に空のテーブルを作成した後、指定の3件を投入する**設計とする。再起動後も初期データ3件から開始し、前回の追加・編集・削除・完了切替の結果は引き継がない。

この点は既存資料と異なる。既存資料自体は変更していないため、実装・受け入れ確認時には開始件数の基準を本書の3件に合わせる必要がある。画面から新規登録するタスクは引き続き必ず未完了とし、初期データに含まれる完了済みタスクとは区別する。

## 2. DB構成と保存期間

H2 Databaseのインメモリ方式（メモリ内にデータを保存する方式）を使用する。接続先の例は次のとおり。

```properties
# 接続が一時的に0本になっても、Javaプロセスの稼働中はデータを保持する。
spring.datasource.url=jdbc:h2:mem:todo;DB_CLOSE_DELAY=-1
```

同一アプリ内で同じ名前のDBを利用し、画面の再読み込みではデータを失わない。アプリのJavaプロセスを終了するとデータは失われ、次回起動時にテーブルと初期データを再作成する。ファイルへの永続化（終了後もデータを残す保存）は行わない。[H2公式: インメモリDB](https://h2database.github.io/html/features.html#in_memory_databases)

SQLファイルの文字コードはUTF-8とする。日時はタイムゾーン情報を含まない値として保存し、本人のWindows PCのローカル日時として扱う。

## 3. テーブル定義

物理名は `todos`、論理名は「タスク」。1行が1件のタスクを表す。NULLは値がない状態、デフォルトは登録時に値を省略した場合の初期値、PK（主キー）は各行を一意に識別する項目を指す。

| カラム名 | 論理名 | 型 | NULL | デフォルト | PK |
| --- | --- | --- | --- | --- | --- |
| id | ID | BIGINT | NO | AUTO_INCREMENT | YES |
| title | タイトル | VARCHAR(100) | NO | - | - |
| description | 説明 | TEXT | YES | NULL | - |
| completed | 完了フラグ | BOOLEAN | NO | false | - |
| created_at | 作成日時 | DATETIME | NO | CURRENT_TIMESTAMP | - |
| updated_at | 更新日時 | DATETIME | NO | CURRENT_TIMESTAMP | - |

`AUTO_INCREMENT` はDBが番号を自動採番する指定であり、固定のデフォルト値ではない。`CURRENT_TIMESTAMP` は現在日時を表す。

### 3.1 各カラムの説明とJava型

| カラム名 | 用途 | Java側の想定型・項目名 | NULL可否 | 初期値 | 自動設定 |
| --- | --- | --- | --- | --- | --- |
| id | タスクの識別、URLで指定された対象の検索 | `Long id` | DBでは不可。Javaでは保存前のみ `null` | DBが採番する値 | 登録時にDBが自動採番。登録後は変更しない |
| title | 利用者が入力したタスク名 | `String title` | 不可 | なし。検証済みの入力値が必須 | なし。アプリが前後の空白を除去して保存 |
| description | タスクの補足説明 | `String description` | 可 | `null`（説明なし） | 未入力・空文字はアプリが `null` に統一。それ以外は入力値を保存 |
| completed | 未完了・完了の区別 | `boolean completed` | 不可 | `false`（未完了） | 通常登録時にアプリが `false` を設定。DBにも同じデフォルトを定義 |
| created_at | タスクを作成した日時 | `LocalDateTime createdAt` | 不可 | 登録時の現在日時 | 登録時に自動設定し、以後は変更しない |
| updated_at | タスクを最後に更新した日時 | `LocalDateTime updatedAt` | 不可 | 登録時の現在日時 | 登録時、および編集・完了切替の保存時に自動設定 |

`Long` は大きな整数と `null` を扱える型、`String` は文字列、`boolean` は `true`／`false` の2値、`LocalDateTime`（`java.time.LocalDateTime`）はタイムゾーンを含まない日時を扱う型である。H2も日時のJava型として `LocalDateTime` をサポートする。[H2公式: データ型](https://h2database.com/html/datatypes.html#timestamp_type)

### 3.2 制約と入力値の扱い

- `id` の主キーで重複とNULLを防ぐ。他のテーブルとの関連や外部キー（別テーブルの行を参照する制約）は設けない。
- 同じタイトルのタスクを登録できるよう、`title` に一意制約（重複禁止）は付けない。主キー以外のインデックス（検索用の索引）は追加しない。
- `title` は前後の空白を除去した後、1～100文字とする。DBの `NOT NULL` だけでは空文字・空白のみを防げないため、サーバー側でも検証する。
- `description` は任意・500文字以内とする。`TEXT` 自体には500文字の上限を指定していないため、サーバー側の標準的な入力検証で制限する。
- 説明を空にして保存する場合は `NULL` に統一する。この保存形式は本書で具体化する。画面では「説明なし」と表示し、その文言をDBに保存しない。
- 利用者が登録・編集する項目は `title` と `description` のみ。ID・日時・登録時の完了状態はフォーム入力から設定しない。

## 4. テーブル作成SQL

DDL（テーブル構造を定義するSQL）の例を示す。定義表の `AUTO_INCREMENT` に相当する採番は、H2の標準的な `GENERATED BY DEFAULT AS IDENTITY` で記述する。主キーは別途指定する。`TEXT` と `DATETIME` はH2が受け付ける型名を用いる。[H2公式: カラム定義](https://h2database.com/html/grammar.html#column_definition)、[H2公式: データ型一覧](https://h2database.com/html/datatypes.html)

```sql
CREATE TABLE todos (
    -- IDはDBが採番するため、通常のINSERTでは指定しない。
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    title VARCHAR(100) NOT NULL,
    description TEXT DEFAULT NULL,
    completed BOOLEAN NOT NULL DEFAULT FALSE,
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    -- DEFAULTは登録時の初期値。更新時の日時設定はアプリが行う。
    updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

### 4.1 自動設定の実装方針

JPAからの登録では、IDをDBの採番に任せ、アプリ側で `completed = false` と作成日時・更新日時を設定する。登録時の両日時には同じ現在日時を使う。SQLで登録する場合は、値を省略すればDBのデフォルトが設定される。

編集・完了切替では、アプリ側で `updatedAt` に現在日時を設定し、業務項目と一緒に保存する。`createdAt` は変更しない。**`DEFAULT CURRENT_TIMESTAMP` だけで更新時の `updated_at` が自動更新されるわけではない。** 本書ではDB側の自動更新指定やトリガー（DB更新時に実行する処理）は追加しない。

DBのデフォルトは、JPAが明示的に送る `null` を自動で補うものとして扱わない。アプリから保存する場合も、必須項目が設定されていることを保証する。

## 5. 初期データ

新しく作成した空の `todos` テーブルに、起動時に1回だけ次の3件を投入する。初期化SQLはテーブル作成後に実行し、JPAとSQLの双方で重複してテーブル作成・データ投入を行わない。

```sql
-- IDと日時を省略し、DBの自動採番とデフォルト値を使用する。
INSERT INTO todos (title, description, completed) VALUES
('Spring Bootを学ぶ', '公式ドキュメントを読む', false),
('買い物に行く', '牛乳とパン', false),
('部屋の掃除', NULL, true);
```

初期状態は未完了2件・完了1件となる。「部屋の掃除」の説明は `NULL` であり、詳細画面では「説明なし」と表示する。これらは初期表示・動作確認用のデータであり、画面からの通常登録で完了状態を選択できることを意味しない。

## 6. 操作とDB処理の対応

| 機能・API | DB処理 | 変更する項目・条件 |
| --- | --- | --- |
| 一覧: GET `/todos` | 全件取得 | `ORDER BY id DESC` で新規追加順の逆順。完了済みも含め、ページ分割しない |
| 登録フォーム: GET `/todos/new` | なし | 空のフォーム表示のみ |
| 登録: POST `/todos` | 1行追加 | タイトル・説明、未完了状態、採番ID、作成・更新日時を保存 |
| 詳細: GET `/todos/{id}` | IDで1件取得 | 変更なし |
| 編集フォーム: GET `/todos/{id}/edit` | IDで1件取得 | 変更なし |
| 編集: POST `/todos/{id}` | IDで対象を取得して更新 | `title`・`description`・`updated_at`。ID・完了状態・作成日時を維持 |
| 削除: POST `/todos/{id}/delete` | IDで対象を確認して1行削除 | 物理削除（行そのものを削除）。削除フラグは設けない |
| 完了切替: POST `/todos/{id}/toggle` | IDで対象を取得して更新 | `completed` を反転し、`updated_at` を更新。他項目は維持 |

本演習では自動採番されたIDの降順を追加順の逆順として使用する。IDは変更しないため、編集・完了切替で一覧の順序は変わらない。採番に欠番が生じても、連続した番号への振り直しは行わない。

登録・更新・削除・完了切替の各保存処理は、トランザクション（まとめた変更を成功時に確定し、失敗時に取り消す単位）内で行う。更新日時も含め、保存失敗時に一部だけ反映させない。入力エラー・キャンセル・対象なしの場合はデータを変更しない。対象なしとDBの読み書き失敗は区別し、API設計書の処理・メッセージに従う。

## 7. 実装後の確認項目

以下は実装後の確認用であり、本書作成時点ではDBを実行して検証していない。

- [ ] `todos` が指定の6カラムで作成され、起動時の初期データが指定の3件になる。
- [ ] 通常登録でIDと日時が設定され、完了状態が未完了になる。同名タイトルも登録できる。
- [ ] タイトル1文字・100文字、説明なし・500文字は保存でき、タイトル空欄・空白のみ・101文字、説明501文字は拒否される。
- [ ] 説明なしはNULLで保存され、詳細に「説明なし」と表示される。
- [ ] 編集・完了切替で更新日時が設定され、作成日時と一覧順は変わらない。
- [ ] 削除は対象1件のみを削除し、入力エラー・キャンセル・保存失敗で既存データを変更しない。
- [ ] 起動中の再読み込みでは操作結果が残り、Javaプロセス終了後の再起動では前回の変更が消えて初期データ3件に戻る。
